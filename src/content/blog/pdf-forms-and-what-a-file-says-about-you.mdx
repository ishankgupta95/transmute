A PDF lands in your inbox with boxes to type into. A rental application, an expenses claim, a school consent form, a supplier onboarding pack. You fill it in, you save it, you send it back — and somewhere between those last two steps sit two questions almost nobody asks. Can the person at the other end change what you wrote? And what else did that file carry out of your machine along with the answers?

Both have specific, checkable answers. Neither answer is quite the one the interface implies, and one of them is the reason this article exists: the obvious way to build a "remove metadata" tool produces a file that still names you, and reports success while doing it.

## A form is a layer sitting on top of the page

A PDF form is not a picture of a form. Somewhere inside the file is an **AcroForm dictionary** — a list of named fields, each with a type (text, check box, radio group, dropdown, list box), a rectangle on some page, and usually a stored *appearance stream* saying what it should look like when drawn.

That distinction explains the most common disappointment. A scanned form, or a form somebody drew as ruled lines and empty boxes in a layout program, has no fields at all. There is nothing there to type into, and no tool can invent one. [Fill PDF Form](/fill-pdf-form) reads the dictionary and, when there is none, says so and hands your file back untouched rather than pretending it did something.

When there *is* a dictionary, you get one control per field, picked from the field's own declared type rather than from a guess about the layout. Fields the document marks read-only are listed with their stored values and locked — and that lock is worth being honest about, because it is not the library's. Measured on pdf-lib 1.17.1: calling `setText` on a field with the read-only flag set neither throws nor is ignored. It succeeds, and the document saves. The lock is the page declining to send a value for that field, and nothing else underneath it.

Field names are not guaranteed unique, either, and that has a consequence. A value is applied by looking the name up in the field list and taking the first match, so a value sent under a name two fields share reaches exactly one of them. Rather than draw two editors that both write to the same place, the second one is locked with a line saying why.

Two more things about filling that are not obvious from the outside.

**Only the fields you actually change are written.** That is not tidiness. Writing to a field marks it for redrawing, and the redraw rewrites that field's default-appearance string with an embedded standard font. Measured on a field whose producer had set it to `1 0 0 rg /Cour 9 Tf`: after a single `setText`, the same field read `1 0 0 rg /Helvetica 9 Tf` — colour and size kept, *font replaced* — while a field left alone in the same document still read `/Cour`. Re-sending a value you never edited would restyle somebody's form for nothing.

**Field text is drawn in a standard PDF font**, which covers the Latin alphabet, accented letters, curly quotes, dashes and the euro sign — and nothing else. Chinese, Japanese, Korean, Cyrillic, Greek, Arabic and emoji cannot be encoded into it at all, and the failure arrives late and useless: the save throws *after* your values are already in the document. So the page checks what you have typed before the run and stops there instead.

## Reading a form is not the same as opening one

A short aside, because it is the kind of thing that goes wrong quietly.

Asking pdf-lib for a document's form *creates* one when the document does not have it. Measured on this repository's own fixtures: the catalog has no AcroForm entry before the call and has one after. Nothing about your file changes, because the reading pass parses the document and never saves — but a tool that asked for the form first and saved afterwards would hand back a document carrying a form dictionary it never had, from a tool whose copy says it only touches form fields.

So the check for "does this document have a form" is read off the catalog *before* anything asks for one. Dropping a PDF onto either page lists what is inside it and writes nothing at all; the changed file only ever arrives as a separate download you asked for.

## Flattening is a one-way door, and it is not redaction

Once the answers are in, the usual next wish is a copy nobody can edit. That is flattening, and [Flatten PDF](/flatten-pdf) does exactly one thing: it takes each field's stored appearance, registers it on the page as a drawable object, draws it into the page's content, and then deletes the field.

Two consequences are worth stating together, because they pull in opposite directions.

Nothing is turned into a picture. The appearance already in the file is re-used as a drawing, so text that was typed into a field is still real text afterwards — measured with a PDF text extractor, a flattened page handed back the typed string and reported zero annotations on it. Your filled-in form stays selectable and searchable, which is almost always what you want.

And it does not go backwards. The fields are gone. Nothing on this site — nothing anywhere, really — turns a flattened PDF back into a form. If the answers might ever need to change, keep the original.

Now the part that gets people hurt: **flattening is not redaction.** It bakes the field's *appearance* into the page. If a value was visible before, it is visible after, selectable after, and copyable by anything that reads page text. What flattening removes is the ability to *edit*; it removes nothing at all from view. A salary figure you flatten is a salary figure you have written into the page more permanently than it was before. If you want something gone from a document, this is the wrong tool and it will leave you feeling protected while the number sits there in the text layer.

It is also not a compression step, whatever else you may have read. Measured on two forms: 5,338 bytes in, 5,409 out; 6,139 in, 6,146 out. The appearances move into the page instead of going away, so the file comes back about the same size and can be slightly larger. If size is the point, that is a separate job for [Compress PDF](/compress-pdf) afterwards.

And it is narrower than "make the document uneditable" suggests. Only *fields* are baked and deleted. Annotations that are not form fields — sticky notes, comments, review stamps — are left exactly where they were, as annotations. Flattening a form does not lock those down.

One flag in the document can widen what flattening touches, and it is worth knowing about because it can bite. A producer can set **/NeedAppearances**, which means "do not trust the appearances I stored, redraw them from the values". When it is set, flattening redraws *every* field before baking — including ones you never went near — and their stored appearance is replaced by a freshly drawn one. That also widens the standard-font problem: measured on a document holding a CJK value in a field nobody had edited, filling a Latin field on its own saved fine, and the same edit with every field marked for redrawing threw on the character it could not encode. So on [Fill PDF Form](/fill-pdf-form), when that flag is set and you have ticked flatten, the check runs over every value in the document rather than only the ones you typed.

Finally, the shape a flattened file comes back in. Flattening empties the field list but leaves the AcroForm dictionary on the catalog, so a document that has already been through this reports *having* a form with zero fields in it. Both pages recognise that and say there is nothing left to bake, rather than running, re-saving the file and calling it a success.

## Some forms refuse to flatten, and the refusal is the feature

The flatten underneath walks the fields in order and deletes each one as it bakes it. If it reaches a field whose appearance it cannot resolve, it throws — and the document at that moment is *half-flattened*. The fields before the failure are already gone and their values already drawn, and the save that follows throws as well. There is no recovering that object; the only correct handling is to look before leaping.

So which fields do it? Ones whose widget has no stored appearance stream. A signature field that was never signed has nothing drawn in it. A radio group whose buttons were never given appearances is the other reliable case — measured, the library's appearance-regeneration pass repairs text fields, check boxes and dropdowns on the way out, but leaves radio widgets with no appearance at all.

Both tools therefore check the whole form first and, if anything is missing, refuse the run and **name the fields** rather than producing a document with those fields silently blank. On [Fill PDF Form](/fill-pdf-form) the flatten box simply turns itself off, and filling still works — the values go in and the form stays interactive.

The unflattering half: that check over-reports. It refuses on *any* missing appearance, and some of those — a text field, a dropdown, a check box — would have been regenerated and flattened perfectly well. There is no way to tell which is which without leaping, and refusing a form that would have worked is a better failure than handing back one that cannot be saved. The check is not a guarantee in the other direction either: a radio group whose appearance dictionary exists but does not contain the state it is currently set to passes the pre-flight and then fails mid-run. When that happens the page names the field it stopped at and your original is untouched, because nothing was ever written to it.

## The part of the file that talks about you

The form is filled, the answers are baked in, the document is finished. It still knows things.

A PDF carries an **/Info dictionary**: Title, Author, Subject, Keywords, Creator, Producer, and the creation and modification dates. In practice Author is frequently your operating-system account name, and Creator and Producer name the software that made the file, often down to the version. None of it is on the page. All of it travels with the file.

It also carries **XMP** — the same sort of information again, in XML, in a packet stored as a stream — and XMP is where tools go wrong.

Here is the measurement, run in this repository against pdf-lib 1.17.1. Build a document with a title and an author in /Info and an XMP packet on the catalog. Then clear it the obvious way: call every metadata setter the library offers — `setTitle('')`, `setAuthor('')`, `setSubject('')`, `setKeywords([])`, `setProducer('')`, `setCreator('')` — and save. Read the result back and the XMP packet is still there, still carrying the document's title and still naming its author in plain text.

Two things went wrong in the same breath. The setters do not touch XMP at all, and they do not even remove the /Info keys they appear to clear — an empty string is written as a lone byte-order mark, so `/Title` survives as an emptied `/Title`. The dictionary after that "clean" still listed all six keys. A tool built this way would report success over a document that goes on stating who wrote it.

XMP is not one place, either. The catalog carries the document's packet; a page can carry its own; and an **image XObject can carry the packet that came with the photograph**. Drop a phone photo into a document and its camera XMP rides into the PDF inside the image, where a catalog-level clean will never see it.

[Remove Metadata](/remove-metadata) deletes the /Info keys instead of blanking them, walks the catalog, every page and every embedded image for XMP streams, and sweeps the objects that deletion orphaned so they are not merely left unreferenced in the file. It tells you how many packets it found before you run it. And after the run it re-reads the file it just produced with the same parser that listed the original and prints what is left — so the line on screen is a measurement of your download rather than a restatement of what the code meant to do.

Two limits it states rather than hides. The trailer's two /ID strings stay in place. And nothing on the pages changes: this alters what the document says *about* itself, never what it shows. A name typed into a page is still on that page — the same boundary flattening has, from the other side. If you want to know what a document still says out loud, run it through [PDF to Text](/pdf-to-text) and read what comes back.

## The image side is a re-encode, and that is not free

The same page takes a photograph, because "what is this file saying about me" is one question to the person holding it. Underneath it is a completely different mechanism, and the difference costs you something real.

There is no cutting Exif out of an encoded picture with a browser canvas. What happens is a decode, a draw and an encode, and the tags are simply not carried across. The download is a **new image built from your pixels**, not your bytes with the metadata removed, and the round trip takes things with it:

- the embedded colour profile is gone, because a canvas works in sRGB;
- anything deeper than 8 bits per channel comes back at 8;
- an animated PNG or WebP keeps only its first frame, and a multi-page TIFF only its first page;
- transparency survives only in PNG and WebP — a JPEG has no alpha channel, so transparent areas are filled white;
- HEIC, HEIF and TIFF come back as JPEG, because no browser can write those containers from a canvas;
- and the lossy containers are recompressed — JPEG and WebP at 92% by default, on a slider you can move. PNG comes off the canvas losslessly, so there is nothing to set there.

That is the honest price of the guarantee, and a page that offers to "remove EXIF" in a browser without listing any of it is not describing what its canvas actually did. It is a genuine limitation rather than a law of nature: a desktop tool working on the encoded bytes directly — `exiftool` is the usual one — can cut the metadata segments out and leave every pixel exactly as it was. A browser canvas has no route to that, which is why this one is upfront about the trade instead. Keep your original if you need the pixels untouched.

One more wrinkle, because the re-encode alone is not actually the whole guarantee: Safari's JPEG encoder writes a fresh Exif block of its own into the picture it just made. So when the output is a JPEG, every APP1 segment is swept back out of the encoded bytes afterwards. The JFIF and colour-profile markers stay, since those describe how to draw the picture rather than where it came from.

Browsers can also quietly substitute the container. A canvas asked to produce a format the browser cannot write does not fail — it serialises PNG instead, and the only place that shows up is the type on the resulting blob. When that happens, the download is named `.webp` and holds PNG bytes, which matters the moment something downstream reads the extension, so the page reads the type back off what the encoder actually produced and says which it wrote.

And an empty list is not proof of a clean file. When the reader cannot parse a picture's metadata block at all, nothing is listed — that is a reader limitation, not a verdict on the file, and it is said on the page rather than left to read like good news. The re-encode still drops what the reader could not see: a PNG text chunk, a Photoshop resource block, anything else riding along in a section nobody enumerated.

If you would rather read the tags than remove them, [EXIF Viewer](/exif-viewer) lists what a photo carries grouped by kind — camera and image, GPS, IPTC, XMP, colour profile — and flags the location group when it finds one.

## The order worth doing this in

Fill the form. Decide whether it needs to stay editable, and flatten only if the answers are final — that door does not reopen. Strip the metadata last. Not because these tools would put it back (the PDF tools here load documents with the library's own metadata stamping switched off, so none of them writes a Producer line of its own on the way out), but because anything *else* you run the file through afterwards very well might.

And none of it is an upload. The PDF work is pdf-lib running in a worker inside this tab; the image path is your browser's own canvas. For a filled-in form that matters in the same way it matters for a password: the file you are being careful with is precisely the file a server-based tool would be asking you to hand over first. [Why browser-based tools are more private](/blog/why-browser-based-tools-are-private) walks through how to check that claim in the Network tab, and it applies to every tool here.

## The short version

**Filling** writes only the fields you change, because writing to a field restyles it in a standard font. The document's read-only flag is honoured by the tool, not by the library underneath it. Non-Latin text cannot be drawn into a form field at all.

**Flattening** bakes each field's appearance into the page and deletes the field. It is permanent, it does not shrink the file, the text stays real text — and it is not redaction. A visible value stays visible.

**Metadata** lives in two places, and clearing the first one leaves the second intact. That is measurable in about a minute, and it is the difference between a tool that works and a tool that says it did.
